# 采集质量监控

管理员进入 **管理后台 → 采集质量**（`/admin/ingestion-quality`）。页面每 5 秒刷新，展示当前 API 实例从启动以来的累计指标和最近 60 个分钟桶；页面隐藏时暂停刷新。API 为 `GET /api/admin/ingestion-quality`，沿用 JWT 和管理员鉴权，禁止子账号访问，响应不缓存。指标读取不查询 ClickHouse，但管理员鉴权仍依赖 PostgreSQL。

## 计数口径

| 字段 | 含义 |
| --- | --- |
| `requests` / `invalid_requests` | HTTP 请求数 / 无法读取、无法解析或空批次请求数；无法确定事件数时不推算事件数量 |
| `received` | 解码后收到的子事件数，包含 engagement；一个 batch 请求可计多个事件 |
| `accepted` | 成功进入内存队列的事件数；是中间阶段，不是落库确认 |
| `filtered` | 接收时或异步处理时按规则过滤，如数据中心 IP、机器人、屏蔽规则、无有效会话的 engagement |
| `rejected` | 入队前拒绝，如字段缺失、站点未验证、频率/配额超限或队列满 |
| `buffered` | 进入 events 写缓冲的事件数，也是中间阶段 |
| `persisted` | events 批次写入收到成功确认的采集事件数；不保证 sessions 同时写入成功 |
| `failed` | 已接收事件处理失败、缓冲满/关闭，或 events 写入重试耗尽后未确认成功；超时可能发生在数据库提交之后，因此不能直接称为“确定丢失数” |
| `pending` | 已入队但还没有终态的事件；按排队、处理、等待写入、写入中分组，并展示最久等待秒数 |

一个事件的终态只记录一次；重试不会重复增加 `persisted`。`accepted`、`buffered` 与终态计数不能相加。接收请求处理完毕后，正常情况下可核对 `received = rejected + filtered + persisted + failed + pending.events`；请求正在校验或入队时存在短暂差额。异步过滤包含在 `accepted` 中，不能用 `received - filtered - rejected` 代替 `accepted`。

分钟桶按**各阶段实际发生时间**计数，而非客户端事件时间；跨分钟处理使单个桶不满足上述等式。累计 `persisted / received` 也不是可靠的成功率：分母包含正常过滤和待处理事件。

采集事件数包含 engagement，与业务报表中排除 engagement 的 events 指标不同。直接导入、种子程序绕过采集入口的写入不纳入该入口的事件计数。

## 两路写入状态

`writers.events` 和 `writers.sessions` 分别展示待写入行、在途行、成功/未确认行、成功/失败批次、重试/失败尝试次数、最近成功/失败时间和最近批次总耗时（包括重试等待）。指标覆盖这两路写缓冲，绕过缓冲直接调用仓储的写入不计入。

会话更新包含旧状态的抵消行和新版本行，**会话行数不能与事件数、会话数直接比较**。事件写入成功、会话写入失败依然可能造成报表不一致，需同时检查两路状态。最久等待时间当前针对采集事件全流程，不是单独的 session 行积压时间；本轮未增加内存字节数监控。

页面在最近 5 个分钟桶出现事件失败、事件等待超过 60 秒，或写入失败晚于最近成功时显示提示。此提示不发送邮件或外部消息，历史累计失败不会自动清除。

## 本轮接收与写入调整

- 单事件和批量子事件使用相同校验。请求体最大 1 MiB，每批最多 100 个子事件；空批次返回 400。子事件可继承批次的域名和 Tracker 版本。
- 通过校验的候选事件一次性入队，容量不足时一个也不进入队列，返回 `503` 和 `Retry-After: 5`，回退本次候选事件预占的月度配额。站点限频仍统计请求尝试，不回退；配额仍采用既有进程内计数和定时持久化机制，不具备跨实例原子配额保证。
- `X-Zenstats-Accepted` / `X-Zenstats-Rejected` 返回入队/拒绝数量；接收时过滤的数据中心或威胁流量通过 `X-Zenstats-Filtered` 披露。混合批次可部分校验通过并返回 202；这些数量不包含异步处理的最终过滤结果，也不标明被拒绝子项的索引，因此不要整批自动重试该 202 请求。
- 已知未知站点/未验证站点返回 400，站点查询故障返回 503。202 仍可能表示进入内存队列，或被明确过滤，不等于落库成功。
- 每次只取有限行数的批次；定时刷新和关闭会继续排空剩余批次。sessions 新增容量上限，旧状态/新状态成对入缓冲，且边界不会拆开相邻抵消/新状态行；接收失败不先修改 session 缓存。
- 单次 ClickHouse 写尝试限制为 5 秒；events 最多尝试 5 次、sessions 最多 3 次，同一批次重试复用 dedup token。任意行追加失败都会终止该批次，避免跳过坏行后误报全部成功；国家代码长度校验防止 FixedString 驱动 panic。
- 关闭时先等待 HTTP 请求结束，再排空采集队列与写缓冲。HTTP 等待预算 10 秒，事件 worker 保留 30 秒等待上限；Compose/K8s 的容器终止宽限期改为 60 秒。大量积压或数据库长时间故障仍可能超过收尾预算。

## 排查顺序与边界

1. 先看数据更新时间、实例 ID 和启动时间，确认页面没有读取失败或切换实例。
2. 拒绝升高时看站点验证、限频、配额和队列原因；过滤升高时检查机器人及屏蔽规则，不直接当作采集故障。
3. 积压或最久等待持续升高时看两路写入在途量、最近成功时间和重试次数，结合 ClickHouse 日志排查连接、超时或数据格式。
4. `failed` / `failed_rows` 增加说明存在处理失败或未获确认写入。结合批次日志判断；**不要直接把原请求整批重放**，客户端没有 event_id 去重，而且会话可能已经更新。

本方案没有 WAL、持久化消息队列或跨轮次失败批次保留。重试耗尽仍会释放失败批次，进程崩溃会丢失尚未落库的内存数据，监控自身也会清零；它无法在重启后还原上个进程的损失。events/session 不存在跨表事务，session 已更新而 events 缓冲拒绝等不一致窗口仍然存在。

每个进程生成独立 `instance_id`，不按站点细分，不跨实例汇总。负载均衡可能使连续刷新落到不同实例，页面会提示切换；排查时应固定目标实例。需要跨重启历史、多实例汇总或主动告警时，应另接外部指标系统。本轮没有做生产吞吐压测。

指标只保留计数、阶段、固定原因代码和时间，不额外记录 URL、IP、访客 ID 或错误正文。
